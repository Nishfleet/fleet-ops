Closes #5743.

**Why:** a transient-overload (503 `overloaded_error`) lane fault of a `pi-issue@<repo>-<N>` unit was re-queued by hand: diagnose, bench the seat, then hand-add a READY-WORK.md row whose `after:` gate waits out the seat's bench (the #2073 hand evidence). READY-WORK.md is a paper ledger (fleet-ops#1493, pinned by `tests/ready-work-deleted.test.sh`) — if nobody re-reads it the issue stays unclaimed. The existing live rail (OnFailure → `pi-issue-failed-reap`) already releases the claim and writes a reclaim cooldown, but that cooldown is a fixed 900s, blind to the seat's bench: a 503 bench is geometrically escalated (600s base, #3531, up to 6h) and can outlast it, so the next worker re-hits the dead seat.

**Change (existing rail only — no new unit, timer, path, or workflow):**
- `bin/pi-issue-failed-reap`: on the reap of an OPEN issue (branch deleted, no open PR — the no-deliverable case), the failed attempt is classified from the last seat's health ledger: `health_class=overload_bench` + `failure_mode=overload_503` with a future `bench_until`. When that bench outlives the cooldown floor (`RECLAIM_COOLDOWN_S`, 900s), the reap appends an absolute `until: <bench_until>` line to the existing cooldown marker, logs the classification, and posts `TRANSIENT-OVERLOAD-REQUEUE` to the heartbeat triage. Not conflated with other deaths: a quota/other health class, an already-expired bench, a bench shorter than the floor, or no seat file at all all fail open to today's fixed 900s cooldown, unchanged. `unit-escalation-write` already excludes `pi-issue@*` (its OnFailure lives here), so the reap stays the single requeue writer.
- `lib/pi-intake-tick.sh`: the #2133 cooldown reader honors the `until:` line — skips the issue (`skipped-reclaim-cooldown-bench`) until the bench expires, then clears the marker and re-claims. Marker line 1 stays the set-timestamp, so the existing #2133 marker shape and tests are untouched. The requeue rides the existing issue-dispatch entry point (intake) — no READY-WORK row.

**Corollary (#3328):** stale claim-branch cleanup for the failed attempt is already mechanized in this same reap — `branch_exists` probe → `gh api …/git/refs/heads/claim/issue-<N> -X DELETE` — so the mutex branch cannot starve the next dispatch; test 5 pins it.
