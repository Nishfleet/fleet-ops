## Summary

Alarm `ESCALATION-COMPLETION-STALE-TRIP` (chain `fbe1286f37cb`, fleet-ops#4919)
flagged that a detector-green STOP-REASON was non-terminal while the
escalation pipeline was idle — a fix that was never closed
(`auditor-resolved`/`boundary:*` required).

Investigation: the underlying chain was already closed by the senior audit
([AUDITOR-LOG] wrote `reason=auditor-resolved`; the live STOP-REASON is now
terminal). Running the detector against live state reports clean:

```
[fleet-escalation-completion] no open escalation chain (STOP-REASON absent or terminal) — clean
EXIT=0
```

So the stuck-trip condition is gone and the reconciler's observe-to-close
(which closed the sibling fleet-ops#4722 the same way) can resolve #4919.

This PR ships the durable mechanical fix (fleet-ops#366): a regression test
proving the **observe-to-close recovery trajectory** — a STALE-TRIP chain
that has gone loud (exit 1) must recover to clean (exit 0) on the next tick
once the auditor advances STOP-REASON to a terminal reason, and must not
re-emit STALE-TRIP. The previous coverage proved the two states
independently (case 5: STALE-TRIP; case 1b: terminal-clean from a fresh
state) but not the transition through the closeout, which is exactly the
path this type of alarm depends on to resolve.

No production logic changed. The issue is NOT closed by this PR (observe-to-close
per the issue body and fleet-ops#362 / #4647); the reconciler closes it when the
detector reports green on a real heartbeat tick.
