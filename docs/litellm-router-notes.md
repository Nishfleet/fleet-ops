A 403 does not cool the row, so the retry skip is overridden by the session-affinity pin (the pin's pre-call filter runs before the skip filter, and the skip filter restores the full list when the exclusion would leave nothing): drilled on 1.105.0, the 403 wall got [403 pick, same-row retry, fallback answer].

NotFoundErrorRetries 1: a 404 ("This model is unavailable for free", a dead slug, an ended preview) is answered by a live row in the same group instead of raising at the caller. It is named separately from DefaultRetries so a future litellm change in how the default resolution reaches a 404 cannot silently re-open the leak; combined with NotFoundErrorAllowedFails: 0 below, the row still parks on the first 404 after that one call.

DefaultRetries 1: the catch-all for every class the named keys miss. A 403 reaches the router from an openai-compatible provider as BadRequestError carrying status 403 (drilled on 1.98.0 and 1.105.0), and BadRequestErrorRetries: 1 (fleet-ops#9375) already granted that class its one attempt on both versions - the attempt re-picks the session-pinned row (the pin outranks the skip list), then the fallback group answers, so no caller sees the 403 either way. A 402 maps to litellm.APIError and gets no analogous named grant: DefaultRetries 1 is what gives it (and APIConnectionError, and any unkeyed class) exactly one in-group attempt on 1.105.0 that 1.98.0 did not give. The named keys keep precedence: 401 and content-policy stay 0, and a 429's single retry stays same-row (litellm retries a 429 by class, so no skip-list entry). A 403 does not cool the row, so a seat whose tier is gone keeps drawing its roughly 1/n share of picks until the row is removed by hand - that is the same path the 2026-09-30 pixel-canary removals took. The flat single-row senior group has no peer and no park on these classes, so its granted attempt re-picks the row itself: one extra in-group pick per call, capped by the value 1.
