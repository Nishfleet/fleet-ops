## Note 11

Was in `config/litellm-proxy.yaml` at line 1196, before `end of file`.

fleet-ops#9050: the two keys 1.98.0 did not have, live since the v1.105.0 image move (fleet-ops#10071). On the pinned image the retry policy is read BEFORE Router.should_retry_this_error (litellm/router_utils/get_retry_from_policy.py, drilled in tests/test_router_retry_policy_no_cross_seat.py), so a named value overrides the class's own raise. get_num_retries_from_retry_policy prefers NotFoundErrorRetries for a status-404 answer, walks the exception's MRO for the named keys, and falls to DefaultRetries for any class the policy does not name. The failed deployment is recorded on litellm's retry skip list (_deployment_ids_to_skip_on_retry, status 403/404/402 all land there) but that list decides WHICH row only when the failed row is out of rotation: a 404 parks the row on NotFoundErrorAllowedFails: 0, so the granted retry went to a live peer (drilled on 1.105.0: 404 pick, peer pick, then the next call went straight to the peer). A 403 does not cool the row, so the retry skip is overridden by the session-affinity pin (the pin's pre-call filter runs before the skip filter, and the skip filter restores the full list when the exclusion would leave nothing): drilled on 1.105.0, the 403 wall got [403 pick, same-row retry, fallback answer].

NotFoundErrorRetries 1: a 404 ("This model is unavailable for free", a dead slug, an ended preview) is answered by a live row in the same group instead of raising at the caller. It is named separately from DefaultRetries so a future litellm change in how the default resolution reaches a 404 cannot silently re-open the leak; combined with NotFoundErrorAllowedFails: 0 below, the row still parks on the first 404 after that one call.

DefaultRetries 1: the catch-all for every class the named keys miss. A 403 reaches the router from an openai-compatible provider as BadRequestError carrying status 403 (drilled on 1.98.0 and 1.105.0), and BadRequestErrorRetries: 1 (fleet-ops#9375) already granted that class its one attempt on both versions - the attempt re-picks the session-pinned row (the pin outranks the skip list), then the fallback group answers, so no caller sees the 403 either way. A 402 maps to litellm.APIError and gets no analogous named grant: DefaultRetries 1 is what gives it (and APIConnectionError, and any unkeyed class) exactly one in-group attempt on 1.105.0 that 1.98.0 did not give.
