## What and why

A no-wall `rate_limit` corpse whose second-chance re-probe failed WITHOUT the seat-health extension re-anchoring a wall (probe timeout / no HTTP response) was force-retired OUT of the live roster immediately (`fleet-ops#3156/#3229`).

Live 2026-09-05: `zenmux z-ai/glm-4.7-flash-free` sat at `c=28` (429, `failure_mode=rate_limit`) as a `seat_dead=true / usable_at=null` terminal corpse with no scheduled retry — the exact no-comeback-clock shape `fleet-ops#2415` leaves for every corpse class. A 429 rate limit resets over a bounded window (`walled_comeback.rate_limit_s`, default 900s), so retiring it as a terminal corpse is wrong.

**`fix(seat)`:** this PR keeps a rate_limit corpse on a bounded comeback instead of retiring it. `reanchor_bounded_comeback` re-writes the ledger to `health_class=rate_limited / seat_dead=false / usable_at=now + RATE_LIMIT_COMEBACK_S` (default 900s, env `FLEET_SEAT_COMEBACK_RATE_LIMIT_S`), preserving the failure count, so the seat re-enters the normal walled path and is re-probed when the clock passes. Only the stuck prober corpse (`comeback_never_released`, non-recoverable) keeps the immediate retire; permanent classes (`credentials_bad`, `quota_exhausted-by-age`) are unchanged. This mirrors the quota_bench corpse comeback-clock fix (`fleet-ops#3377/#3512`) for the rate_limit class.
