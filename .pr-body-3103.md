Repair the systemd-networkd-wait-online flapping failure on netcup-rs2000
and record why masking it is the wrong fix (fleet-ops#3103).

## The incident

`systemd-networkd-wait-online.service` (a root-level systemd unit) spun in
failed state for ~25h, paging SystemUnitFailed every alert cycle with an
escalation that never terminated in a repair. The unit shows the same flap
class as the earlier fleet-ops#2751 incident on this exact unit.

## Root cause (reproduced live on the host)

The netplan-generated `.network` left eth0 **Setup stuck at `configuring`**
(networkd waited on a DHCPv6 lease that never arrives on this host), so
wait-online could not reach its online condition and exited 1:

- `networkctl status eth0` -> `State: routable (configuring)`, `Online state: online`
- `systemd-networkd-wait-online --timeout=5 --any -o routable -i eth0` -> `Timeout occurred while waiting for network connectivity`, exit 1
- wait-online journal: repeated `Timeout occurred ...` -> `Result=exit-code` every ~15min on 2026-09-03

The host was online the whole time (eth0 routable, default route via
159.195.212.1); wait-online was a false negative, not a real outage.

## The repair

The unit healed when eth0's setup completed. It now verifies green and healthy
live on netcup-rs2000:

- `networkctl status eth0` -> `State: routable (configured)`, `Online state: online`
- `systemd-networkd-wait-online --timeout=5 --any -o routable -i eth0` -> exit 0
- `systemctl show systemd-networkd-wait-online.service` -> `ActiveState=active Result=success ExecMainStatus=0`

For this class (a unit waiting on an interface/DHCPv6 lease that never
completes), the durable repair is the network/setup reaching `configured` —
not masking.

## Why masking was rejected (evidence, 2026-09-04)

The `masked_units` rail (fleet-ops#2122) is the fleet's mechanism for units
that can never be healthy here, but it is the WRONG mechanism for this unit:

- **The unit can be healthy.** It is now (see above), so a
  "can never be healthy" mask is semantically false.
- **Masking does not hold.** netplan owns `systemd-networkd-wait-online` and
  regenerates + re-enables it on netplan apply, silently removing an
  `/etc/systemd/system` mask within minutes (observed live: a mask placed at
  12:36 IST was replaced by a netplan re-enable at 12:38 IST).
- **A `masked_units` entry is self-defeating**: `live_check`/
  `count_unmasked_units` reports the unit as not-masked (verified:
  `UNMASKED_COUNT=1`), so the manifest would claim a permanent violation that
  apply_rebuild cannot satisfy.

mechanical-mechanism-impossible: <the fleet-ops repo cannot durably mask or repair a
root-level, netplan-owned systemd unit (masking needs root, is undone by netplan
regeneration, and the unit is not actually unhealable); the class is already
detected by the existing SystemUnitFailed -> auto-filed-issue loop and the
fleet-ops#2751 flap-holding Prometheus cross-check. The repo-side durable artifact
is this runbook note so the failed mask attempt is not repeated.>

## What changed

- `docs/bare-metal-rebuild.md`: document the incident root cause, the repair
