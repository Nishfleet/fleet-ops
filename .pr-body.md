# fix(scout): mechanical leak detector for ScoutEffectivenessLow pipeline

## What changed

The `ScoutEffectivenessLow` alert fires when the scout runs but its output is not translating to merged work. The alert reports the symptom; this PR adds the mechanical isolation the issue's accept requires.

1. **`lib/scout-effectiveness.py`** gains a `claimed` stage metric (`fleet_scout_issues_claimed{repo="0509"}`), closing the last attribution gap in the pipeline `filed -> survive_intake -> agent_ready -> claimed -> merged_14d`. Claimed = carries the `agent-in-progress` label; GitHub labels are sticky across close, so claimed-then-merged issues stay counted.

2. **`bin/fleet-scout-leak-canary`** (new, heartbeat-tier1 block 45, MANIFEST-installed, no new timer), satisfying accept (a)+(b)+(c):
   - reads the same node-exporter .prom gauges the alert reads (single source of truth — the canary can never contradict the alert's own counts),
   - isolates the **dominant** leak stage among four gates: `duped` (filed - survive_intake), `never-ready` (survive_intake - agent_ready), `unclaimed` (agent_ready - claimed), `unmerged` (claimed - merged_14d). The accept names three of these; `never-ready` is the gate between them and is the live dominant leak (filed=117, survive=117, agent_ready=1 at 2026-09-04) — a detector that skipped it would report "no dominant leak" while the pipeline starves, the exact failure this issue bans,
   - auto-files a targeted `fix(scout-leak):` mechanism issue naming the stage, the live counts, and a stage-specific mechanism hypothesis (intake dedup too aggressive / promotion gate dead / no healthy seats / claim branches not merging),
   - observe-to-closes when the alert resolves (ratio >= 0.1 with runs > 0 — the issue's termination condition) or when a stage's leak drains to 0,
   - does NOT report "effectiveness low" without isolating the stage (no-dominant runs LOUD `SCOUT-LEAK-NO-DOMINANT` and file nothing — the upstream green-and-empty class belongs to scout-futility-check, fleet-ops#454/#2468).

Prevention mechanism (fleet-ops#366): the detector runs every heartbeat tick (every scout cycle), auto-files, and observe-to-closes on alert resolution.

Design (design-it-twice): **Candidate A** — exporter-owned attribution, canary reads the live gauges (adopted). **Candidate B** — canary recomputes the pipeline from gh itself (rejected: duplicates the 14d/dupe-hour/merge-window attribution the exporter owns = information leakage, heavy per-tick gh load, and could contradict the alert's counts). Grafted from B: nothing — its only real idea (a gh cross-check) adds no value because the exporter already did the attribution.

organ-heartbeat: bin/fleet-scout-leak-canary not-an-organ: exports no heartbeat metric; it is a reaction detector over the scout-effectiveness organ's own gauges (that organ already ships its absent() rule and fleet-organs.json entry).
