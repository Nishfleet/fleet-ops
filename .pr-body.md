## Summary

The drift canary's observe-to-close wiring (fleet-ops#620) only posted a
`resolved-at:` comment on a resolved drift issue — it never closed the
issue. With no automated closer for the drift/hot-patch class, resolved
issues lingered open until a human or worker closed them by hand
(fleet-ops#1156 sat open across many heartbeat ticks with two
`resolved-at:` comments; #1302 was closed by hand the same way).

This completes the two-tick observe-to-close pattern already used by
`fleet-exec-review-canary` (fleet-ops#729) and `fleet-decisions-ledger`
(fleet-ops#650):

- Tick 1 (green, no marker): post `resolved-at:` (unchanged).
- Tick 2+ (green, marker already present): `gh issue close --reason completed`.

A still-red class never reaches this code — the matching check `fail_loud`s
before `observe_close_drift_issues` runs — so a dirty drift issue is never
closed. The close is gated by `FLEET_OPS_DRIFT_CLOSE` (default 1, on in
production); tests and one-off runs set it to 0 for the comment-only path,
mirroring `CLOSE_ISSUES` on the sibling canaries.

This is the mechanical prevention for the "resolved drift issue lingers
open" class (fleet-ops#366): future hot-patch/off-main/etc. drift issues
auto-close on the next green heartbeat tick once their `resolved-at:`
marker has landed, so no worker ever needs to `gh issue close` for the
class.

The #1156 drift itself (live `fleet-heartbeat-tier1` hot-patched with
`_propagate_crash`) is already resolved: PR #1364 landed the proper
rc-propagation refactor that superseded the hot-patch, and the live file
is now a symlink to the deploy-clone copy (md5 match, drift canary green).
