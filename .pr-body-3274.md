## Manager loop for heavy/keystone issues (part 1/9)

When the packet's first line is `difficulty: heavy` or `difficulty: keystone` (written by the intake tick from the issue's labels/body), the pi-issue worker now runs as MANAGER: it plans phases, delegates each to a fresh stock `worker` subagent, reviews each phase diff with the stock `reviewer`, ticks `.fleet/plan.md`, and ships the PR. Light issues stay flat.

### What changed
- `prompts/worker.md`: added a `Manager mode (heavy|keystone)` section that keys off the packet's difficulty header. It uses Pi's STOCK pieces end to end (planner/worker/reviewer agents, `prompts/implement.md`, `prompts/implement-and-review.md`, `prompts/scout-and-plan.md`, plan-mode/todo extensions) and only ADDS the phase loop and the stall rule on top — it does not re-implement any stock prompt or the plan format. No new `bin/` file (fails research-before-build-check by design).
- `tests/worker-prompt-manager-mode.test.sh`: replay drill that grep-locks every manager-mode directive, rebuilds heavy/keystone/light packets the way the tick does, asserts the stock subagent pieces exist on disk, and checks the CI host.
- `tests/pi-issue-start.test.sh`: hosts the new test (fleet-ops#82 — workers have no Workflows permission, so no new ci.yml line).

### Constraints honoured
- Wording: 'extremely well', never 'perfect'.
- Manager batches subagent calls (<= 8 per call, multiple calls); never forks the stock extension to raise the constant.
- Stock pieces only; the manager prompt may ADD the phase loop and stall rule, never re-implement planner/reviewer/worker prompts or the plan format.
- Stall rule at both levels: a phase with no box ticked in 10 min is closed with what works and a `stalled: phase N — <reason>` note; the manager may amend the plan with a one-line reason in `.fleet/plan.md` (implementer proposes, manager decides).
